# sql_equiv Project Memory

## Working Principles
- **When you fix a bug, sweep for the same pattern elsewhere.** Fixing `applyIdentityLaws` without checking the other 4 rewrite functions left the same bug in all of them.
- **When you forget to do something manually, automate it.** ci_sparkline caught CI anomalies, `/audit` caught unsound rewrites, the pre-commit hook reminds you to audit. Each tool exists because "just remember" failed. This compounds — each tool frees attention for the next one.
- **When you build a parser, test it against known input and check every field.** Exit code 0 and plausible-looking output aren't enough — verify parsed data matches expectations (e.g. `assert parsed.guard is not None`). The rewrite audit regex bug went unnoticed because the display accidentally looked correct.
- **Allowlist > blocklist for type guards.** `isDefinitelyNonBool` (blocklist) left gaps for `.col`, `.case`, `.agg`, `.subquery`. `isDefinitelyBool` (allowlist) is safer — only fire when you can prove it's safe. Applies broadly: when guarding rewrites, prove the precondition holds rather than trying to enumerate all violations.
- **When you guard a function, sweep for inline copies.** The `optimizeExpr` inline `NOT NOT => inner` was an unguarded duplicate of `eliminateDoubleNegation`. The guard didn't help until the inline copy was also fixed.
- **Eval-based tests have blind spots; use AST equality when eval can't distinguish.** `NOT NOT NULL = NULL` evaluates identically whether or not the rewrite fires. AST checks catch the difference.
- **Test the pass you think you're testing.** `optimizeExpr` constant-folds `5*0` before `simplifyArithmetic` runs — calling `optimizeExpr` didn't exercise the guard. Call the specific pass directly.
- **Tests must match the guard's requirements.** After switching to `isDefinitelyBool`, tests using `col("x")` stopped triggering identity laws. Use definitely-typed expressions (e.g. comparisons for bool, int literals for int).
- **When the audit flags a convention violation, fix it — don't rationalize.** The CONCAT `_` vs `some _` divergence was flagged as "minor/not exploitable" but Copilot correctly caught it. Conventions exist to be followed uniformly; reasoning about individual exceptions defeats the purpose.
- **Axiom premises should mirror the implementation's predicate form.** `evalSelect_filter_all_false` used `≠` (propositional) but `List.filter` in `evalSelect` uses `==` (boolean). Every call site needed a bridging step. Writing the axiom as `== ... = false` eliminated that friction. General rule: specs/axioms that describe code should use the same operators the code uses.
- **When converting axioms to theorems, update the ratchet count in the same PR.** The build succeeds locally but CI checks `axiom_count_minimum.txt`. Easy to forget because it's a separate file from the proof work.
- **Sweep means enumerate, not "fix the one I see."** PR #120 needed 3 review rounds because each fix was applied to one instance, not all. Hoisted `rightRows` in left_join but not cross/inner (review #2). Fixed axioms but not tests (review #2). Tested one branch but not all three (review #3). The sweep must be mechanical: list every instance, check each one.
- **Infrastructure axiom tests need one case per match arm.** If an axiom has `match on_ with | none => ... | some cond => match eval... with | true => ... | _ => ...`, that's 3 branches → 3 tests minimum. One "interesting" test is not enough.
- **After finishing proofs, grep for every `private` helper to confirm it's used.** Proof exploration leaves dead code — helpers written for abandoned approaches. Lean's linter doesn't flag unused `private theorem`. Mechanical check: each private name should appear ≥ 2 times in the file (definition + usage). PR #122 shipped 4 unused helpers that Copilot caught.
- **Planning quality correlates with review quality.** PR #120 (minimal plan) → 3 review rounds. PR #121 (detailed plan with proof sketches, dependency ordering, risk assessment) → 0-comment Copilot review. The upfront time on proof sketches and helper lemma signatures pays back in fewer review iterations.
- **Null propagation must be broad (`some (.null _), _`) not targeted (`some (.null _), some (.bool true)`).** Targeted arms (only bool/null + bool/null) break distributivity because `OR(NULL, AND(FALSE, INT))` = NULL (inner short-circuits, outer propagates) but `AND(OR(NULL, FALSE), OR(NULL, INT))` = error (NULL + non-bool = error). Broad arms (`some (.null _), _` after short-circuit) make null uniformly absorbing, fixing distributivity for `some _` inputs. But value-level distributivity is STILL false for `none` (error) inputs because `AND(FALSE, error)` short-circuits the error away. Expression-level distributivity is correct (SQL operands are always boolean) — use axioms.
- **When changing evaluator semantics, cascade through ALL dependent evaluators.** Adding AND/OR null propagation also broke BETWEEN (defined via Value.compare match, not AND(GE,LE)). The fix: redefine BETWEEN as `evalBinOp .and (evalBinOp .ge ev evlo) (evalBinOp .le ev evhi)` — makes it consistent by construction and eliminates the 90-line exhaustive proof.
- **Review feedback can cascade harder than the original change.** The PR #125 evaluator rewrite was self-contained. The reviewer's `_` → `some _` tightening (4 lines) broke 4 proven theorems, a tactic example, and 2 LSpec tests across 7 files. When a reviewer suggests tightening a match arm, immediately check: what other code pattern-matches on the same type and relied on the broader arm?
- **Sweep includes examples and property tests, not just proofs.** Tactics.lean `example` blocks are compile-time tests. When an axiom signature changes (e.g. adding `isBoolValued`), examples using that axiom break. LSpec property tests with broad generators (`BoundedGroundExpr`) will catch value-level claims that narrower generators (`BoolGroundExpr`) miss — a failing property test after a semantics change is a signal to restrict the test's domain, not just fix the assertion.
- **SELECT * WHERE axioms reduce to list filter algebra.** `evalSelect_star_where_eq_filter` decomposes `SELECT * FROM t WHERE p` into `(baseRows.map ([] ++ ·)).filter p_pred`. After `simp only [List.nil_append, List.map_id']` cleans up the map, all WHERE axioms (`filter_and`, `filter_commute`, `filter_idempotent`, `predicate_pushdown`) reduce to `list_filter_and_eq` + `evalBinOp_and_true_iff`. The universal decomposition: rewrite both sides → simplify maps → apply filter algebra → close with AND-true-iff.
- **Observe before reasoning about Lean's elaborator.** When `rw` fails, don't speculate about what compiled form a lambda "should" have — use `trace_state` to see what it *actually* has. Speculative reasoning about elaborator behavior is unreliable and compounds: each wrong guess spawns another attempt (bridge lemmas, `show ... from by`, `simp only` variants) that fails for the same invisible reason. One `trace_state` after `rw [evalFrom_left_join]` would have diagnosed the compiled lambda form divergence in Batch 19 immediately; instead, ~70% of the time on `left_join_filter_null_is_inner` was spent on approaches that all failed for the same undiagnosed cause.

## Optimizer Soundness Patterns
- **Boolean rewrites use `isDefinitelyBool` allowlist** (PR #101). Only fires for expressions statically guaranteed boolean (bool lit, logical/comparison ops, isNull/isNotNull, between, inList, exists). This replaced the `isDefinitelyNonBool` blocklist which missed `.col`, `.case`, `.agg`, `.subquery`.
- **Arithmetic identity rewrites use `isDefinitelyNonInt` blocklist** (PR #100). Guards `a+0=>a` etc. against string/bool/null/comparison/logical operands. Arithmetic annihilation (`a*0=>0`) only fires for known int literals. `0/a=>0` was removed entirely (null + div-by-zero).
- LSpec `BoundedGroundExpr` generators don't produce `.col` or `.func`, so property tests can't catch column-ref-evaluates-to-wrong-type-at-runtime. The type guards are the primary defense for those cases.
- When adding a new rewrite, always run `/audit <function>` before committing.

## PR Workflow
- **ALWAYS work in a branch, never commit directly to master.** Create a feature branch first (`git checkout -b claude/...`), commit there, push, then open a PR. Only commit to master if explicitly requested.
- **Start a NEW branch from master for each new task/PR.** Don't reuse branches from previous PRs — working on a stale branch and then rebasing causes unnecessary merge conflicts.
- Do NOT request Copilot review on PRs. No `@copilot please review` comments.
- **Compact between PR review rounds.** After opening a PR and before addressing each review, compact the conversation. This resets anchoring on "what I already did" and forces re-reading the actual diff, making sweeps natural. The PR diff is the source of truth for review rounds, not conversation history.
- **Multiple review rounds are the safety net.** PR #120 needed 3 rounds to catch all sweep misses. This works because each round reviews in depth — not just the new changes but the surrounding context. Don't short-circuit the process by merging after one "looks good" round.
- **Write a failing test first before writing the real test.** For each new test category, first write a version that *should* fail (e.g., compare optimized result against a deliberately wrong baseline, or assert a wrong row count). Run it, confirm it fails, then fix it to the real assertion. This catches vacuous tests where both sides silently return empty/error due to wrong column refs, bad table names, etc. Anti-vacuity guards help but a red-then-green cycle is stronger.

## Lean Proof Tactics
- **When automation chokes on nested structs, keep the outer constructor opaque and use surgical `rw` lemmas.** Unfolding 3+ struct layers (BitVec→UInt32→Char) creates terms too complex for `omega`/`simp`. Instead, prove small bridge lemmas per layer and chain `rw` calls. See `toNat_ofNat_of_isValid` in Comparison.lean.
- **Constructor/destructor pairs need two lemmas: "strip projection" and "round-trip identity".** E.g. `(Char.ofNat n).toNat = n` clears conditions inside if-then-else; `Char.ofNat c.toNat = c` closes the final goal. They serve different roles.
- **`have h := by omega; rw [if_pos h]` for conditionals through opaque types.** When `split` can't find an `if` buried under an opaque constructor, manually resolve each branch.
- **Simple cases succeeding can mask hard cases.** If a "slightly harder" variant of a working proof fails, switch strategies early — don't force the same automation.
- **`Value.null` carries `Option SqlType` — evaluator functions that return `.null none` lose type info.** When proving identity axioms like `CONCAT("", e) = e`, the evalFunc must preserve the null's type (`=> some (.null t)`, not `=> some (.null none)`) or the proof fails with `⊢ none = n`. Check whether existing evaluator arms normalize nulls before copying their pattern.
- **Axioms about identity elimination are almost always unsound without a type precondition.** `f(identity, e) = e` fails when `e` has the wrong type: LHS returns `none` (type mismatch) but RHS returns `e`'s raw value. Always check: what happens for int/string/bool/null/none inputs? Add preconditions like `isStringOrNullValued` or `isBoolValued`.

## Lean Proof Tactics (continued)
- **`simp only [Value.compare, evalBinOp]; cases compare <;> rfl`** — universal tactic for proofs where one side is a `match` on `Value.compare` results and the other uses `evalBinOp` calls (e.g., `evalBetween_expansion`). Works because `simp` reduces both the match and the overlapping evalBinOp decision tree, leaving only the `Ordering` variable. Does NOT work for evalBinOp-vs-evalBinOp (commutativity/associativity) where both sides have overlapping patterns.
- **`cases v <;> cases w <;> simp [evalFunc, ...]`** — compact alternative to 20+ explicit match arms for `evalFunc`-based proofs. Must case-split `Value` constructors (not just `Option Value`) for `simp` to reduce `evalFunc` dispatch.
- **`generalize hv : evalExprWithDb db row expr = v; cases v` for compiled match goals.** When `rw` with a bridge lemma fails because Lean's compiled match has a different internal form than the lemma's LHS, generalize the scrutinee and case-split. Each Value constructor case closes with `simp; exact ih`. This is the standard approach for `filterMap` bodies that pattern-match on `evalExprWithDb` results.

## Infrastructure Axiom Proof Patterns
- **`evalSelect_limit_offset`**: decomposes `evalSelect db (... limit offset)` into `take/drop` on the base (no limit/offset) result. When `limit`/`offset` are concrete (`some n`, `none`), `rw` closes the goal by definitional reduction — no `simp` needed.
- **Private helper lemmas (`evalSelect_SN`, `evalSelect_S0`, `evalSelect_0N`)**: specialize the infrastructure axiom for concrete limit/offset Option values, producing clean RHS without `let` bindings. Essential when goals have TWO `evalSelect` calls (e.g., `≤` inequalities) — using raw `rw [evalSelect_limit_offset]` twice causes the second `rw` to match the `base` expression from the first rewrite. With helpers + `cases limit`, each branch uses a clean specialized lemma.
- **`generalize evalSelect db (... none none) = base`**: after `rw` with helpers, replaces the long expression with a short variable for `simp`/`omega` reasoning.
- **`offset_too_large_empty` was unsound** for `limit = some L` with the original definition (count from `limit none` instead of `none none`). Fixed by measuring count from the base query with no limit/offset.
- **`rw` with infrastructure axioms produces joint matches and `let` bindings.** `rw [evalFrom_inner_join]` introduces `match on_, lr, rr with` (compiled joint match) and `let combined := lr ++ rr`. These block `simp` matching. Fix: `dsimp` reduces both, but only at top level — it does NOT enter lambda bodies.
- **The `dsimp` → `simp only [evalExprWithDb_lit]` combo** is the standard pattern for evalFrom join proofs. `dsimp` normalizes `let`/match structure; `simp only` enters lambda bodies and reduces `evalExprWithDb` on literals plus the resulting match.
- **`simp only [h]` fails when `h` has `let` bindings the goal has expanded.** Build standalone lemmas (e.g., `List.filterMap_none`, `List.filterMap_some_comp`) whose LHS matches the *normalized* form instead.
- **`ext` on lists produces `getElem?` goals; use `funext` for function extensionality.** `ext lr` after `congr 1` on a `flatMap` equality destructures into per-index goals, making induction hypotheses unusable. `funext lr` keeps the goal structural.
- **Induction hypotheses don't track goal simplifications.** When `simp [evalExprWithDb_lit]` simplifies the goal, `ih` retains the original form. Either `simp ... at ih ⊢` or use a standalone lemma that matches the simplified goal.
- **`rw [evalFrom_left_join]` normalizes lambda forms.** `fun (k, _) => k == col` in hypotheses stays as `fun x => match x with | (k, snd) => ...`, but in the goal (after `rw`) becomes `fun x => x.fst == col`. Fix: bridge with `have h' : List.find? (fun (x : String × Value) => x.fst == col) lr = none := hOriginal lr hlr`. `have` type ascription accepts definitional equality.
- **`congr 1` before `rw [List.filter_eq_self]`** when goal is `(filter p l).length = l.length`. The iff in `filter_eq_self` matches `filter p l = l`, not the `.length` wrapper.
- **`dsimp only []` reduces `let` bindings + `if (decidable bool)` in one step.** Infrastructure axioms (e.g. `evalExprWithDb_inList`) produce `let ev := ...; let result := ...; if neg then X else Y`. For concrete lists, `simp [List.foldl]` handles everything. For abstract lists, `simp [List.foldl]` can't reduce the foldl, and `simp only [ite_false]` doesn't fire because the condition is `false = true` (a Prop), not `False`. `dsimp only []` solves both: it inlines `let` (definitional) and reduces `if false = true then X else Y` via the `Decidable` instance (also definitional).
- **Foldl induction needs explicit `have step` for accumulator bridging.** When proving `foldl f (eval acc) = eval (foldl g acc)` by induction, the IH expects `eval (new_acc_expr)` but the goal has `evalBinOp .or (eval acc) (evalBinOp .eq ...)`. Bridge with `have step : evalBinOp ... = eval (Expr.binOp ...) := by rw [evalExprWithDb_binOp, evalExprWithDb_binOp]; rw [step]; exact ih _`.
- **`simp [evalBinOp]` doesn't see through `Option.map`.** `evalBinOp .eq` on non-null values produces `(v.eq w).map Value.bool`. Subsequent `evalBinOp .or` can't reduce because simp doesn't know the map result is `some (.bool _)`. Fix: small helper that case-splits on `Option Bool` directly (e.g. `or_false_map_bool`). Pattern: `cases o with | none => rfl | some b => cases b <;> rfl`.
- **Count `rw [evalExprWithDb_binOp]` calls by counting `Expr.binOp` nodes.** `Expr.binOp .and (Expr.binOp .ne e a) (Expr.binOp .ne e b)` = 3 nodes = 3 rewrites, not 4. The Nth+1 call fails with "pattern not found."
- **BoolOrNullOrNone (BNN) proofs need explicit 9-case splits, not `all_goals`.** `rcases hl; rcases hr; simp; all_goals (cases bl <;> rfl)` fails because `bl` only exists in the `hl=bool` branches. Use nested `rcases` with `·` focus bullets and case-split the relevant Bool variable in each branch.
- **`private def` in ValueLemmas.lean can't be used from Comparison.lean.** If a predicate like `isBoolOrNullOrNone` is needed across files, don't mark it `private`. Same applies to helper lemmas: `list_filter_and_eq` was private in SemanticsCore.lean but needed in Semantics.lean for `predicate_pushdown` (PR #147).
- **`dsimp only []` may not reduce `if true = true then ...` after `evalExprWithDb_inList`.** Follow with `simp only [ite_true]` to eliminate the conditional.
- **When adding induction invariants (like BNN), use `refine ih _ _ ?_ h_inv` to place the invariant last.** `apply ih _ h_inv` puts `h_inv` in the wrong argument position because `apply` fills args left-to-right.
- **When an opaque native function blocks proofs, refactor to use provable equivalents.** `String.startsWith`/`String.endsWith` go through `memcmpSlice` (kernel-opaque). Replace with `List.head?`/`List.getLast?`/`List.isPrefixOf`/`List.isSuffixOf` for identical behavior that `simp` can reduce.
- **`generalize` before `rw` when a subexpression appears in both matched and unmatched positions.** `rw [h]` replaces ALL occurrences. `generalize hx : subexpr = x` first abstracts the one you want to keep, so `rw` only touches the other.
- **`prefix` is a keyword in Lean 4** — can't use it as a variable name. Use `pfx` instead. Similarly `notation`, `infix`, `postfix`.
- **`set` is not available without Mathlib.** Use `generalize` or `let` instead for introducing local definitions in tactic mode.
- **IN subquery and evalBinOp .eq have different null/type-mismatch semantics.** IN uses `v.eq subVal == some true` (returns `false` for null/type-mismatch), while `evalBinOp .eq` returns `some (.null none)` for null and `none` for type mismatch. Any axiom equating IN with BinOp.eq needs a type-compatibility precondition (`∃ b, val.eq v = some b`).
- **CASE short-circuits don't preserve error propagation.** `CASE WHEN cond THEN literal ELSE e` returns the literal regardless of whether `e` would error. So `e ≃ₑ CASE WHEN cond THEN literal ELSE e` needs a precondition that `e` doesn't error (for rows where cond is true).
- **For evalCase proofs, use `have hcond : evalExprWithDb ... cond = some (.bool true/false)` then `rw [evalCase_cons_true/false _ _ _ _ _ _ hcond]`.** Can't use bare `rw [evalCase_cons_true]` because it needs the hypothesis proof.

## Partial Def Workaround (PR #130)
- **3-file split pattern**: `SemanticsBase.lean` (types/helpers) → `SemanticsCore.lean` (non-partial mirrors + proofs) → `Semantics.lean` (partial defs + bridge axioms + final theorems). Necessary because `partial def` = `opaque` in Lean 4 kernel.
- **WFR functions never reduce by `rfl`** — not even from imported modules. `WellFounded.fix`/`Acc.rec` are kernel-opaque. Use `simp [f]` instead, which generates equational theorems on the fly.
- **For complex WFR branches, use `rw [f.eq_def]` not `simp [f]`.** `simp [f]` applies the equational theorem AND tries to reduce the resulting compiled match — which fails silently for complex branches like `.case` (reports argument as "unused"). `rw [f.eq_def]` applies the rewrite without reduction, letting you chain with separate lemmas.
- **`if false = true` doesn't reduce by `dsimp only []`; use full `simp`.** Bool `if b then` compiles to `if b = true then`. `dsimp` reduces `.fst` but not the Decidable instance for `@Eq Bool`.
- **`simp [f]` fails when `partial def`s are in the environment.** Importing a file with `partial def` blocks equational theorem generation for non-partial functions in the same namespace. Prove in a file that imports NO partial defs.
- **WFR `decreasing_by` for Prod projections**: `omega` can't relate `sizeOf pair.fst` to `sizeOf pair`. Fix: `obtain ⟨a, b⟩ := pair; simp [Prod.mk.sizeOf_spec]` then `omega`.
- **`List.map_congr_left` bridges partial applications in `List.map`.** When `simp only [bridge]` can't rewrite inside `args.map (evalExprWithDb db row)`, use `congrArg (evalFunc name) (List.map_congr_left fun e _ => bridge.symm)`.

## Gotchas
- **Never import `Batteries.Data.List.Perm`** — it transitively imports `Batteries.Tactic.Alias` which makes `alias` a keyword, breaking `Optimizer.lean` and `PredicatePushdown.lean` which use `alias` as a variable name. Prove `perm_ext_iff_of_nodup` from core lemmas (`perm_iff_count` + `Nodup.count`) instead.
- `testDb "tableName"` returns raw rows without qualification. `evalFrom` qualifies columns as `"alias.col"`. When manually iterating db rows for join-match tests, must qualify: `row.map fun (k, v) => (s!"{qualifier}.{k}", v)`
- `evalStmt` returns `(Database, Option Table)` — comparing full results can fail when optimizer changes expression structure (e.g., column expression differs). Prefer expression-level `evalExprWithDb` comparison for optimizer equiv tests.
- **`List.mem_cons_self` has all implicit args in Lean 4.27.0.** Write `h a List.mem_cons_self`, NOT `h a (List.mem_cons_self a rest)`. Similarly, `List.mem_cons_of_mem a hx` still works (first arg is explicit).
- **`ring` tactic is not available** (no Mathlib). For `n + m * n = (m + 1) * n`, use `rw [Nat.add_mul, Nat.one_mul, Nat.add_comm]`.
